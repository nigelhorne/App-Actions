Run GitHub Actions workflows locally

App::Actions runs a GitHub Actions workflow on your own computer, in Docker containers, so a broken workflow can be debugged without a commit, a push and a wait for a runner. 

cpanm App::Actions

action-run check ~/src/my-project
action-run .github/workflows/ci.yml .

The workflow is read as GitHub would read it: jobs are selected, matrices are expanded, service containers start, and each step runs in turn inside a long-lived job container with the project mounted. Files and installed modules stay between steps, exactly as they do on GitHub. When the run is over, the containers and networks are removed and the images are kept as the next run's cache.

  • The same steps, locally

    Jobs, matrix expansion, containers, services, working directories, shells, if: conditions and ${{ }} expressions.

  • GitHub's step files

    GITHUB_ENV, PATH, OUTPUT, STATE and STEP_SUMMARY written by one step are seen by the next.

  • Matrices in parallel

    One job per CPU by default, each with its own container, network and log, so a wide matrix uses the machine instead of queueing.

  • A real preflight

    The daemon, Linux containers and bind mounts are probed, and every image is pulled before the first job starts.

  • Kept images and logs

    A run's images become the next run's cache, and parallel job logs survive the containers. Both can be listed and pruned.

  • Documents for CI

    check, preflight, cache and logs each print a versioned JSON document with a published schema.

How a run works

  1. The workflow file is read and each job's matrix is expanded — action-run --list prints the jobs without running anything.
  2. The host is checked: the Docker daemon must be reachable, running Linux containers, and able to bind-mount both a temporary directory and the project.
  3. The images the selected jobs need are prepared — job images, service images and docker:// action images — four at a time by default, before any container starts.
  4. For each job, a private Docker network is made, the job's service containers start, and one long-lived job container starts with the project mounted in it.
  5. Each step is executed in that container with docker exec, so files and installed modules persist between steps.
  6. The job's containers and network are removed and the result is reported. Images stay, unless --no-keep-images is given.
# what would run, and in what order
action-run --list .github/workflows/ci.yml

# the Docker commands, without starting anything
action-run --dry-run --verbose .github/workflows/ci.yml .

# one job only, with a secret
action-run --job test --secret CODECOV_TOKEN="$CODECOV_TOKEN" \
           .github/workflows/ci.yml .

What it does not do

Only Linux jobs can be emulated: jobs with runs-on: macos-* or windows-* are skipped, not failed. Remote actions are not fetched — actions/checkout and shogo82148/actions-setup-perl become no-ops because the project is already mounted and the image is chosen from the requested Perl version. Local composite and JavaScript actions do run. Job outputs, needs.*.outputs and timeout-minutes are not implemented. The whole list is here.
