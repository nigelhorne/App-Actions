JSON and CI

Four commands can print a versioned JSON document instead of prose: check, preflight, cache and logs. Each one publishes the schema it is written against, so an assertion can be written against the contract rather than a copy of it.

DocumentPrinted bySchemaDescribes
checkaction-run check --jsonaction-run schema checkThe host, the daemon, the mount probes and the problems found.
preflightaction-run preflight --jsonaction-run schema preflightThe same, plus every image the run needs and how preparing it went.
cacheaction-run cache --jsonaction-run schema cacheThe images runs kept, their sizes and ages, and what a prune did.
logsaction-run logs --jsonaction-run schema logsThe per-job logs parallel runs kept, and what a prune did.

Versioned, and checked before it is printed

Every document carries a schema_version naming the shape it was written for, so an assertion can say which shape it expects instead of failing on a key that moved. Before a document is printed it is checked against its own schema: a key that was added, removed or retyped without the schema changing exits 70 with a message naming the first mismatch, and nothing is written to standard output. A CI job therefore never receives a document its own contract would reject.

The schema and the version it declares come from the module that produces the document, so the two cannot disagree. The preflight document is versioned separately from the check document, because images can change without the check document changing.

check --json

{
  "schema_version": 2,
  "ready": true,
  "problems": 0,
  "host": { "os": "linux", "name": "Linux", "perl": "5.40.0", "archname": "x86_64-linux" },
  "docker": { "bin": "docker", "client": "29.9.1", "daemon": "29.9.1", "containers": "linux" },
  "image": "alpine:3.20",
  "mounts": [
    { "host": "/tmp/action-run-check-XXXX", "container": "/action-run-check", "ok": true },
    { "host": "/src/project", "container": "/check-project", "entries": 17, "expected": 17, "ok": true }
  ],
  "issues": [ { "problem": "...", "remedies": [ "..." ] } ]
}

The top-level keys and the keys of docker are always present; a value that could not be discovered is null, so an unreachable daemon shows as "daemon": null rather than a missing key. Each entry in mounts carries host, container and ok, and the project entry also carries entries and expected.

preflight --json

{
  "schema_version": 3,
  "ready": true,
  "problems": 0,
  "pull_concurrency": 4,
  "host": { "os": "linux", "name": "Linux", "perl": "5.40.0", "archname": "x86_64-linux" },
  "docker": { "bin": "docker", "client": "29.9.1", "daemon": "29.9.1", "containers": "linux" },
  "image": "perl:5.38",
  "mounts": [ ... ],
  "issues": [],
  "images": [
    { "image": "perl:5.38", "source": "job 'test'", "status": "pulled" },
    { "image": "postgres:15", "source": "service 'db' of job 'test'", "status": "present" }
  ]
}

source says what needs the image: a job, a service container, or a docker:// action naming its job. status is pulled, present, failed, skipped or deferred. A failed entry also carries error, and the same failure appears in issues with a remedy. ready is true only when the checks passed and every image is present or was pulled.

An image built from a value no job has produced yet — another job's result, for instance — is deferred: image is null, and expression and error say what could not be resolved and why. A deferral is not a problem, so it leaves ready and problems alone; the job resolves and prepares that image itself before it starts. This is what lets CI distinguish an image that was verified from one that could not be named yet.

cache --json and logs --json

{
  "schema_version": 3,
  "generated_at": 1792540920,
  "cache_file": "/home/me/.cache/action-run/cache.json",
  "docker": { "bin": "docker", "reachable": true },
  "images": [
    { "image": "alpine:3.20", "pulls": 3, "last_used": 1792540800, "age": 120, "size": 12345678, "present": true },
    { "image": "perl:5.38", "pulls": 1, "last_used": 1792440000, "age": 100920, "size": null, "present": false }
  ],
  "totals": { "images": 2, "size": 12345678, "present": 1, "missing": 1 },
  "prune": null
}

generated_at is the epoch second the document was made, so age needs neither machine to agree on a clock. A daemon that cannot be reached leaves its reachable flag false and the sizes, the present values and the counts that depend on them null, so an assertion can tell unknown from missing rather than reading 0 as either. After --prune the prune key is an object holding removed, freed, forgotten and the failed images that stayed in the record; the document is printed even when a removal failed, and the exit status is 1.

The logs document has the same shape of header — schema_version, generated_at, logs_directory, logs, totals, prune — with each log carrying run, name, path, size, mtime and age.

Assertions in a CI job

# the host is ready, and the engine really is Linux
action-run check --json | jq -e '.ready and .docker.containers == "linux"'

# every image the workflow needs could be prepared
action-run preflight --json .github/workflows/test.yml . \
    | jq -e '.ready and ([.images[].status] | all(. == "pulled" or . == "present"))'

# published schema, and a document checked against it elsewhere
action-run schema preflight > preflight-schema.json
action-run preflight --json .github/workflows/test.yml . > preflight.json
action-run validate preflight preflight.json

# how much disk the kept images take
action-run cache --json | jq -r '.totals.size'

validate is the piece that works anywhere: it needs neither Docker nor the workflow, just the schema name and a saved document. That is how a result produced by another job or on another machine can be checked where Docker is not available.

Also usable from Perl

use JSON::PP;

my $result = App::Actions->new(workflow_file => 'ci.yml')->preflight(json => 1);
print JSON::PP->new->canonical->encode($result->{summary}), "\n";
exit $result->{exit};   # 0 or 2

With json => 1 nothing is printed, so the caller's output can be a single document. summary is the report as data, with ready as a JSON boolean, and it has already been validated against the schema. App::Actions->json_schema('check') returns a schema as a hash reference, which is also what action-run schema prints.
