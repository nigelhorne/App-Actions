Limits and pitfalls

A local run is not a runner. Knowing where the two differ is the difference between a tool that saves time and one that reports success for something GitHub would reject.

Limitations

  • Only Linux jobs can be emulated. Windows and macOS jobs are skipped.
  • Local composite and JavaScript actions run; remote actions and local docker actions cannot. Checkout, setup-perl, cache, artifact and Codecov actions are no-ops. --strict-actions turns an unknown action into a failure instead of a skip.
  • JavaScript actions need node in the job image.
  • Job outputs, needs.*.outputs and timeout-minutes are not implemented.
  • Images are pulled concurrently only where fork() is reliable. On Windows they are pulled one at a time, because Perl's emulation of fork() shares the parent's handles with the child.
  • The host may run UNIX or Windows; only the containers are Linux. Command output is captured without fork or a piped open, and paths, volumes and permissions are handled in a platform-neutral way. Step scripts, the sudo and apt shims and event.json are written with LF line endings.

Pitfalls

Run action-run check first

Most failures before the first job are a Docker problem — not running, Windows containers, a drive not shared — and check names the remedy for each one. A run makes the same probes itself and prints the same report, but running it deliberately is quicker to read.

Secrets are on the command line

--secret and --env values are visible to every user of the computer in ps while the run is in progress. The Docker command lines the tool starts keep them hidden, and hints in the workflow are redacted from printed commands, but the tool's own arguments are not. On a shared machine, pass a test value — or pass the secrets through a Perl caller instead.

Give the project directory when the workflow is elsewhere

If the workflow file is not inside a .github/workflows directory, the project directory must be the second argument. Otherwise the repository root found from the workflow's path is used.

Skipped is not failed

macOS and Windows jobs are skipped, and unsupported remote actions are skipped with a warning. The exit status can therefore be 0 even though some jobs did not run; the summary lists them as skipped.

Images are kept after the run

That is the cache working. Use action-run cache to see what it holds, action-run cache --prune to free the space, or --no-keep-images for a one-off image.

A setting in a file or the environment beats the command line

An App__Actions section in ~/.conf/local.yaml (or base.yaml), or an App__Actions__parallel variable, wins over --parallel and the other run options. When an option seems to be ignored, look there. Values from those places are not checked, so a mistyped one is accepted silently.

A UNIVERSAL logger takes the messages off the terminal

Object::Configure applies a UNIVERSAL section of universal.yaml to every class that uses it, this one included. If that section has a logger writing to a file or to syslog, a failed step is reported there and not on standard error. Give this module its own logger in an App__Actions section, or pass one.

--older-than needs a unit

30d or 2 weeks, not 30. An unreadable duration is a usage error, not a silent fall back to no filter.

Exit status 70 is a bug

It means a JSON document did not match its own schema. Nothing was printed, so a CI job cannot mistake a malformed document for a good one. That is this distribution's fault, not your workflow's: please report it.

Only run workflows you trust

A workflow's container.volumes and options can mount any folder of your computer into a container, as they can on GitHub's own runners. Running a workflow from an unknown source is running its code on your machine.

Run as yourself or root

With --user set to another user, the job's files — secrets included — must be readable by every user of the computer, and a warning says so.

Design weaknesses that remain

  • The runner plans the run and hands the work to five parts — images, containers, steps, parallel jobs and the report — each in its own module under App/Actions/Runner/. The parts are built from copies of the runner's options rather than given the runner, so they can be tested alone, but a change to an option after construction is not seen by them.
  • Errors raised through the catalogue are App::Actions::Error objects carrying the message key as a stable code; the errors of Check, Docker, Expression, Process, Cache and Logs are still strings.
  • The option rules are one table, but the options are checked twice: once by App::Actions and once by the runner, which is a public class and so checks its own arguments.
  • Settings merged in from configuration files and App__Actions__* variables are applied after the arguments have been checked, so they are not checked at all.
  • Not everything a run prints goes through the logger: progress, command echoes and the summary are output and stay on standard output.
