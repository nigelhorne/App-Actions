Workflow support

App::Actions implements the parts of a workflow that are useful for local testing. Everything else is skipped, with a warning where silence would mislead, or refused where pretending would be worse.

A job's life

Every selected job goes through the same shape, whether it came from a matrix or not:

  1. A private Docker network is created for the job and its services.
  2. The job's service containers start on that network, with the aliases and ports the workflow gives them. A service that stops, or that a restart policy keeps bringing back, stops the run with the state and restart count the daemon reports and the last lines the container printed.
  3. One long-lived container starts with the project mounted in it, as the configured user or the image's default.
  4. Each step that passes its if: condition is run in that container with docker exec. Files and installed modules stay between steps, as on GitHub.
  5. The containers and network are removed — unless the run is kept — and the images stay as the next run's cache.

Understood

  • Jobs — selected by id or display name, with env, defaults, container and services.
  • Matrices — strategy.matrix is expanded before anything runs, so --list shows every combination and each entry gets its own container, network, runner directory and log.
  • Containers and services — image, env, ports, volumes, options and credentials, with matrix values resolved.
  • Steps — run, uses, with, env, if, shell, working-directory and continue-on-error.
  • Conditions — if: on jobs and steps, including failure() and always(), so the steps after a failed one run only when the workflow asks them to.
  • Expressions — ${{ }} over contexts, with comparisons, logic, indexing and the usual functions.
  • Shells and working directories — the job's and the step's, with the job's defaults.
  • GitHub's step files — GITHUB_ENV, GITHUB_PATH, GITHUB_OUTPUT, GITHUB_STATE and GITHUB_STEP_SUMMARY. A value written by one step is seen by the next.
  • continue-on-error and fail-fast — a failing matrix entry does not cancel the others when the workflow says it should not.

Which image a job gets

A job with a container: uses that image. Without one, the job uses --image (default ubuntu:latest, or ubuntu:24.04 for runs-on: ubuntu-24.04). A job that sets up Perl with shogo82148/actions-setup-perl uses --perl-image, which is perl:%s by default.

Actions

Kind of actionWhat happens locally
Local composite action (./.github/actions/…) Read and run, including actions used inside other actions. Their images are prepared before the first step.
Local JavaScript action Run, so the job image needs node.
docker:// actions The image is pulled during preparation and the action's container is run. A local docker action cannot be run.
actions/checkout, shogo82148/actions-setup-perl No-ops: the project is already mounted, and the Perl image is chosen from the requested version.
Cache, artifact and Codecov actions No-ops.
Any other remote action Skipped with a warning. --strict-actions makes that a failure instead.

Nothing is downloaded from GitHub, so a remote action cannot silently succeed: it is skipped, or it fails when you ask it to.

Not implemented

  • Job outputs, needs.*.outputs and timeout-minutes.
  • macOS and Windows runners. A job with runs-on: macos-* or windows-* is skipped, not failed, and the exit status can be 0 even though some jobs did not run. The summary lists them as skipped.
  • Remote actions, as above.

Running as root, and sudo

Many job images run as root and have no sudo, which would make an ordinary sudo apt update step fail locally but pass on GitHub. When the image has no sudo and the container runs as root, a small sudo shim is placed on PATH, along with an apt shim, so those steps mean what they mean on a runner.

Diagnosing a container that will not start

--explain prints what each container would be told to run, without starting anything and without contacting the daemon. A service has no command of its own in a workflow, so its block reports (the image's own) for the entrypoint and command, or the entrypoint its options replace. That is what tells a service that stops on start-up from one that was given a bad command. 

==> Service 'helper' of job 'test'
    container  action-run-0123abcd-2-svc-test-0-helper
    image      postgres:16
    entrypoint (the image's own)
    command    (the image's own)
